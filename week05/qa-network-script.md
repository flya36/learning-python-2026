# 一、HTTPS 握手（约 100 秒）

## 骨架（先记这 6 个词）

问题 → 方案 → 矛盾 → 四步 → 证书 → 1.3 差异

## 口述稿

> HTTP 是明文传输，链路上有三类风险：
>
> **窃听、篡改、冒充**
>
> 。HTTPS 就是在 HTTP 下面加一层 TLS，用三件事对应解决：加密防窃听、完整性校验防篡改、证书防冒充。
> 它的核心难点是
>
> **密钥怎么安全交换**
>
> 。对称加密快，但密钥不能明文传；非对称加密能安全传密钥，但太慢。所以是
>
> **混合方案**
>
> ：握手阶段用非对称，数据传输用对称。
> 以 TLS 1.2 为例，握手四步：
> 第一步，客户端发 ClientHello，带上自己支持的加密套件和一个随机数；
> 第二步，服务端回 ServerHello，选定套件、再给一个随机数，并附上自己的证书；
> 第三步，客户端
>
> **验证证书**
>
> ——CA 签名链、域名是否匹配、是否过期 —— 通过后生成第三个随机数，用证书里的公钥加密发出去；
> 第四步，双方各自用这三个随机数
>
> **派生出同一把会话密钥**
>
> ，之后全程用这把密钥做对称加密。
> 这里有个容易讲错的点：
>
> **证书不是用来加密的**
>
> ，它解决的是 "这个公钥到底属于谁"。没有证书，中间人可以把
>
> **自己的公钥**
>
> 发给你，你用它加密，中间人全能解开。
> TLS 1.3 把握手简化到 
>
> **1-RTT**
>
> ，去掉了 RSA 密钥交换，只允许 ECDHE，所以具备前向安全性，弱算法也全部删除。
> 落到我们项目上：CourseMate 的登录接口和 JWT 走 HTTPS，否则 token 在链路上就是明文，抓包就能冒充登录。

## 追问预案



| 追问               | 一句话答                                      |
| ---------------- | ----------------------------------------- |
| 为什么不用非对称加密传全部数据？ | 慢。RSA 比 AES 慢几个数量级，只适合传密钥，不适合传业务数据        |
| 中间人攻击具体怎么防住的？    | 靠证书。中间人拿不到 CA 签发的、绑定目标域名的证书，伪造证书过不了签名链验证  |
| 会话密钥为什么会一样？      | 不是传输的，是双方用同样的三个随机数 + 同样的算法各自算出来的          |
| HTTPS 就一定安全吗？    | 不一定。客户端不校验证书、或设备装了恶意根证书（比如抓包工具）时，仍会被中间人解密 |

# 二、Cookie / Session / JWT（约 120 秒）

## 骨架（先记这 5 个词）

存哪 → Cookie → Session 痛点 → JWT 结构 + 短板 → 归属校验

## 口述稿

> 这三种方案的本质区别是 **"状态存在哪"**：Cookie 存在浏览器，Session 存在服务端，JWT 存在 token 自己身上。
> **Cookie**
>
>  就是浏览器本地的一段文本，同域名下每次请求自动带上。它本身不是认证方案，只是存储和自动携带的载体。安全属性主要三个：
>
> `HttpOnly`
>
>  让 JS 读不到，防 XSS 偷 cookie；
>
> `Secure`
>
>  只在 HTTPS 下发；
>
> `SameSite`
>
>  控制跨站请求要不要带，防 CSRF。
> **Session**
>
>  的思路是服务端存状态。用户登录后服务端建一条 session，把 sessionid 通过 cookie 下发给浏览器，之后每次请求带上 id，服务端查表拿到用户。优点是
>
> **能主动失效**
>
> —— 删掉 session 就下线；痛点是服务端要存，而且
>
> **多机部署必须用 Redis 集中共享**
>
> ，否则请求打到另一台机器就掉登录。
> **JWT**
>
>  是无状态方案，三段结构：header 放算法，payload 放业务数据比如 user_id 和过期时间，signature 是签名。这里有个常见误区要澄清：
>
> **payload 只是 base64url 编码，不是加密**
>
> ，任何人拿到都能解出内容，所以 JWT 里绝不能放密码；
>
> **签名防的是篡改，不是防窥探**
>
> 。
> JWT 的优点是服务端不存、天然支持多机扩展、移动端友好。但它有个
>
> **致命短板：签发后在过期前无法主动失效**
>
> 。用户改密码或者被封号，旧 token 还能用。工程上靠 "短过期 + refresh token"，或者维护 Redis 黑名单。
> 放到我们项目：CourseMate 用 JWT 做认证，密钥从 
>
> `.env`
>
>  读，
>
> `exp`
>
>  设 24 小时。但有一点我特别清楚 ——
>
> **JWT 只回答 "你是谁"，不回答 "这个资源是不是你的"**
>
> 。所以光有认证不够，还必须做
>
> **资源归属校验**
>
> ：查文档时比对 
>
> `owner_id`
>
> ，不属于当前用户返回 403。
>
> **401 是没登录，403 是登录了但没权限**
>
> ，这两个状态码不能混。

## 追问预案



| 追问                              | 一句话答                                                                 |
| ------------------------------- | -------------------------------------------------------------------- |
| JWT 能存密码吗？                      | 不能。payload 只是 base64url 编码，可被直接解码查看                                  |
| 怎么做登出？                          | JWT 本身做不到。要么短过期 + refresh token，要么维护 Redis 黑名单                       |
| token 放 localStorage 还是 Cookie？ | 各有风险：localStorage 怕 XSS 窃取；Cookie 怕 CSRF，需要配 `SameSite` 和 `HttpOnly` |
| Session 为什么需要 Redis？            | 多机部署时各机本地内存不共享，请求打到别的机器就查不到 session，所以要把状态集中存                        |
| 401 和 403 有什么区别？                | 401 是身份未认证（没登录 /token 无效）；403 是身份已确认但无权限                             |

# 三、面试技巧（比背稿更重要）



1. **先说结论，再展开**。开头一句 "本质区别是状态存哪"，面试官立刻知道你抓到了核心。

2. **主动暴露一个坑**（"这里有个容易讲错的点"、"它的致命短板是"）。这比背得流利更能显示理解深度。

3. **必须落回项目**。每段结尾联系 CourseMate，这是你和 "只会背八股的人" 的区分点。

4. **被追问答不上来时**：`"这块我只在实际用过的层面理解，比如我们项目里是……更底层我没有深挖"`—— 比硬编强得多。

5. **不要一次说完所有细节**。留一个口子给面试官追问，反而显得从容。
