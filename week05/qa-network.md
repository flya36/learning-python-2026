# 题 1 · HTTPS 握手流程

## 一、先回答"为什么要 HTTPS"

HTTP 是明文的，裸奔在链路上会暴露三类问题：

| 问题 | 说明 |
| --- | --- |
| 窃听 | 中间人抓包就能看到密码、Token、请求体 |
| 篡改 | 中间人改响应内容（比如把转账金额改掉） |
| 冒充 | 中间人伪装成服务端（DNS 劫持 / 伪造站点） |

HTTPS = HTTP + TLS，就是用 TLS 解决这三件事：**加密（防窃听）、完整性校验（防篡改）、证书（防冒充）**。

## 二、核心矛盾：对称 vs 非对称

| 类型 | 特点 | 用途 |
| --- | --- | --- |
| 对称加密（AES） | 加解密同一个密钥，**快** | 传业务数据 |
| 非对称加密（RSA/ECC） | 公钥加密、私钥解密，**慢**（大数运算） | 只在握手阶段交换密钥 |

**为什么混合**：非对称太慢，不可能用它传全部数据；但对称的密钥又不能明文传输（会被抓）。所以：**用非对称加密把对称密钥安全送过去，之后全程用对称**。

## 三、TLS 1.2 握手（四步，要能画出来）

```
客户端                                                       服务端
   | ① ClientHello（支持的加密套件 + 随机数 R1）  ----------->  |
   | ② <---- ServerHello（选定套件 + 随机数 R2）+ 证书（含公钥） |
   |                                                          |
   | ③ 验证证书链（是否 CA 签发、域名是否匹配、是否过期）        |
   |    生成随机数 R3，用服务器公钥加密后发送 -----------------> |
   |                                                          |
   | ④ 双方各自用 R1 + R2 + R3 派生出同一把会话密钥             |
   |                                                          |
   | <========= 之后全部用会话密钥做对称加密 ==========>        |
```

**关键点**：
- 会话密钥是**双方各自算出来**的，不是谁传给谁
- 每次连接都换新密钥（R1/R2 是随机的），所以即使某次密钥泄漏也不影响历史流量（这叫"前向安全"，TLS 1.3 做得更好）

## 四、TLS 1.3 简化了什么

| 项 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 握手轮次 | 2-RTT | **1-RTT**（甚至 0-RTT） |
| 密钥交换 | RSA 或 ECDHE 都可能 | **只允许 ECDHE**（前向安全） |
| 加密套件 | 一堆老旧算法（RC4、3DES…） | 精简，去掉所有弱算法 |
| 证书 | 明文传 | 也加密传 |

**一句话**：1.3 把"能用但不安全"的选项全删了，握手更快。

## 五、证书到底解决什么

很多人以为"证书是用来加密的"——**不对**。证书解决的是"**这个公钥到底属于谁**"：

- 没有证书：中间人可以把**自己的公钥**发给你，你用它加密，中间人就能解密（中间人攻击）
- 有证书：公钥和域名绑定，并由 CA（证书颁发机构）签名。你验证签名 → 确认"这个公钥确实是 `coursemate.xxx` 的"
- 验证三件事：**CA 签名链**、**域名是否匹配**、**是否在有效期内**

所以：**加密靠算法，身份靠证书**。

## 六、联系 CourseMate

```
V0.3 上线后：前端 → https://api.../auth/login（密码、JWT 全在 TLS 通道里）
            没有 TLS 的话，JWT 在链路上就是明文，抓包直接冒充登录
```

- `.env` 里放 `JWT_SECRET`，TLS 保护"传输中"，密钥保护"签发环节"——两层不同的事
- 本地开发 http://127.0.0.1 可以裸跑；一旦对外提供服务必须 HTTPS（现在很多免费证书 + 反向代理就能做）

# 题 2 · Cookie、Session、JWT 的区别

## 一、一句话区分：状态存在哪

| 方案 | 状态存在哪 | 浏览器存什么 | 服务端存什么 |
| --- | --- | --- | --- |
| Cookie | 浏览器 | 键值对明文 | 不存 |
| Session | **服务端** | 只有 `sessionid`（放 Cookie 里） | 用户会话数据（内存/Redis） |
| JWT | **Token 自己身上** | Token | **不存**（无状态） |

## 二、Cookie

- 就是浏览器本地存储的小段文本，**同一域名下每次请求自动带上**（`Cookie: xxx=yyy`）
- 属性要会讲：
  - `HttpOnly`：JS 读不到（防 XSS 偷 Cookie）
  - `Secure`：只在 HTTPS 下发送
  - `SameSite`：跨站请求是否带（防 CSRF，`Lax`/`Strict`/`None`）
  - `Max-Age` / `Expires`：过期时间
- **Cookie 本身不是认证方案**，它只是"存储 + 自动携带"的载体

## 三、Session

流程：

```
1. 用户登录 → 服务端创建 session，生成 sessionid
2. 服务端把 session 数据存起来（内存 / Redis），sessionid 通过 Cookie 下发
3. 下次请求带上 sessionid → 服务端查表拿到用户
4. 登出 = 服务端删掉这条 session
```

**优点**：能随时主动失效（删 session 就下线了）；数据在服务端，安全。

**痛点**：
- 服务端要存（内存占用）
- **多机部署要共享** → 必须引入 Redis 之类的集中存储，否则请求打到另一台机器就"掉登录"
- 跨域场景 Cookie 不好带（移动端 App 更麻烦）

## 四、JWT

结构（三段，用 `.` 分隔）：

```
header.payload.signature
  ↑        ↑          ↑
算法声明  业务数据   签名
```

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxIiwiZXhwIjoxNzAwMDAwMDAwfQ . xxxxxx
```

- **payload 只是 base64url 编码，不是加密**——任何人拿到都能解出 `user_id`、`exp`
- 能防的是**篡改**：改了 payload，签名就对不上（除非有 `JWT_SECRET`）
- 所以：**JWT 里绝对不能放密码、密钥等敏感信息**

流程：

```
1. 登录成功 → 服务端用 JWT_SECRET 签发 token（含 user_id + exp）
2. 前端保存，每次请求放 Authorization: Bearer <token>
3. 服务端验签 + 检查 exp → 取出 user_id，不需要查库
```

**优点**：无状态（服务端不存），多机部署天然可扩展，移动端友好。

**致命短板**：
- **无法主动失效**——token 签发后，在过期前一直有效。用户改密码/被封号，旧 token 还能用
- 解决办法：黑名单（存 Redis）、短过期 + refresh token
- token 变长（每次请求都带）

## 五、三者对比表（面试可以直接照着说）

| 维度 | Cookie | Session | JWT |
| --- | --- | --- | --- |
| 状态位置 | 浏览器 | 服务端 | Token 内 |
| 服务端存储 | 无 | 有（内存/Redis） | 无（无状态） |
| 能否主动失效 | — | ✅ 删 session | ❌ 需黑名单 |
| 多机扩展 | — | 难（要共享存储） | 易 |
| 防篡改 | 无 | 依赖 sessionid 不可猜 | 签名保证 |
| 典型风险 | XSS / CSRF | sessionid 劫持 | token 泄漏、无法吊销 |

**常见组合**：JWT 放 Cookie 里（`HttpOnly` + `Secure`）或放请求头——放 Cookie 能防 XSS 读取，但要处理 CSRF；放 header 要防 XSS 窃取。

## 六、联系 CourseMate（V0.3 要落地的）

```
POST /auth/login  {email, password}
  → 校验密码 → 签发 JWT（payload: {sub: user_id, exp: now + 1440min}）
  → 前端存 token，之后每次请求带 Authorization: Bearer xxx

后端依赖：get_current_user
  1. 取 header 里的 Bearer token
  2. jwt.decode(token, settings.jwt_secret, algorithms=["HS256"])  ← 验签 + 自动校验 exp
  3. 失败 → 401（token 无效/过期）
  4. 成功 → 返回 user_id
```

**关键认知（面试常问的深水区）**：

> JWT 只回答"**你是谁**"，不回答"**这个东西是不是你的**"。

所以 V0.3 光有认证还不够，必须再加一层**资源归属校验**：

```python
# 例：查文档时必须校验归属，否则 A 用户能读 B 用户的文档
document = db.get(Document, document_id)
if document.owner_id != current_user.id:
    raise HTTPException(403, "无权访问该文档")
```

- 认证（401/未登录）和授权（403/没权限）是两件事，状态码也不同
- `JWT_SECRET` 只从 `.env` 读，绝不放代码/仓库
